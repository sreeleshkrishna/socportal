# Role-based access control

_Generated by `backend/scripts/generate-docs.ts` from the code and the live database. Do not edit by hand: change the code, then run the script again._

Access is deny-by-default. The backend checks the caller's role on every API call (`requirePermission`, `src/auth/authorize.ts`); roles come from the Keycloak token. `tests/rbac.test.ts` loops over every route and every role.

## Roles and permissions

| Permission | What it allows | Tier 1 analyst | Tier 2 analyst | Incident responder | SOC manager | Auditor |
|---|---|:-:|:-:|:-:|:-:|:-:|
| `case:read` | View cases, timelines, tasks, evidence lists, indicators; download and verify evidence; export reports | ✔ | ✔ | ✔ | ✔ | ✔ |
| `case:create` | Create cases | ✔ | ✔ |  | ✔ |  |
| `case:update` | Edit case fields; add notes, tasks, playbooks, evidence, indicators and techniques; normal status transitions | ✔ | ✔ | ✔ | ✔ |  |
| `case:escalate` | Escalate a case | ✔ | ✔ |  | ✔ |  |
| `case:assign` | Assign or reassign cases and tasks |  | ✔ | ✔ | ✔ |  |
| `case:close` | Close a case |  |  | ✔ | ✔ |  |
| `audit:read` | View the audit log and verify its hash chain |  |  |  | ✔ | ✔ |
| `user:read` | List users |  |  |  | ✔ |  |
| `dashboard:read` | View the metrics dashboard |  |  |  | ✔ | ✔ |

No role holds `system:escalate`. It exists only for the automatic escalation done by the SLA worker, so no user can perform that transition.
